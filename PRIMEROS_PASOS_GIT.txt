manualmente: crear este documento no ha modificado el repositorio real.

Ejecuta los comandos uno a uno, sin copiar los indicadores de la terminal

1. CONCEPTOS BÁSICOS
===================
Git: programa que registra versiones de los archivos en tu ordenador.
GitHub: servicio donde puedes alojar repositorios Git y colaborar.
Repositorio: archivos del proyecto y su historial, guardado en .git.
Fork: copia del repositorio original en tu cuenta de GitHub, vinculada al
original. Aquí publicaremos los cambios personales.
Clone: descarga de un repositorio y su historial al ordenador. Se hace una vez.
Branch o rama: línea de trabajo dentro del repositorio. Usaremos desarrollo.
Commit: registro local de los cambios seleccionados, con un mensaje explicativo.
Push: envío de commits locales a una rama de un repositorio remoto.
Fetch: descarga información e historial remoto sin integrar esos cambios en
los archivos de tu rama de trabajo.
Pull: hace fetch e integra cambios en la rama actual. En esta guía usamos
--ff-only para que se detenga si necesita combinar historiales divergentes.
Pull request (PR): propuesta para incorporar cambios a otra rama o repositorio.
No se crea automáticamente al hacer push. Para proponer cambios al tutor,
habría que abrirla expresamente y revisar su repositorio y rama de destino.
Remoto: nombre corto de un repositorio remoto. origin y upstream son nombres
convencionales; las URL son las que determinan a qué repositorio apuntan.
Área de preparación: selección de cambios hecha con git add para el próximo
commit. Guardar un archivo, hacer commit y hacer push son pasos distintos.

2. PREPARACIÓN INICIAL: HERRAMIENTAS Y AUTENTICACIÓN
=================================================
Necesitas una cuenta de GitHub, Git y GitHub CLI (gh). R y RStudio servirán
para trabajar con CalTools; esta guía configura Git, no las dependencias de R.

Comprueba las herramientas:
  git --version
  gh --version

Si macOS solicita las herramientas de desarrollo para Git, sigue su asistente.
También puedes iniciarlo con:
  xcode-select --install

Si falta gh, consulta https://cli.github.com/ e instala GitHub CLI para macOS.
Si ya utilizas Homebrew, puedes instalarlo con:
  brew install gh
No ejecutes esa línea si Homebrew no está instalado.

Inicia sesión:
  gh auth login

Elige GitHub.com, HTTPS y acceso mediante navegador. Si te pregunta si quieres
autenticar Git con tus credenciales de GitHub, responde que sí. Comprueba:
  gh auth status

Debe aparecer la cuenta correcta (peauelea96 en este caso). Si Git no queda
configurado para usar esa autenticación, ejecuta:
  gh auth setup-git

No escribas contraseñas ni tokens en archivos del proyecto. GitHub no acepta
la contraseña de la cuenta como contraseña de Git por HTTPS.

Los commits necesitan nombre y correo. Sustituye los ejemplos antes de ejecutar:
  git config --global user.name "Tu nombre"
  git config --global user.email "TU_CORREO_DE_GITHUB"

Puedes usar el correo privado noreply exacto que muestra GitHub en Settings >
Emails. --global aplica a todos tus repositorios; si quieres identidad distinta
solo aquí, usa los mismos comandos sin --global dentro de CalTools.

3. CONFIGURACIÓN DESDE CERO: FORK, CLONE Y DESARROLLO
==================================================
Haz esto solo si todavía NO tienes la carpeta CalTools configurada.

A. Crear primero el fork
Abre https://github.com/pgsegador/CalTools en el navegador, pulsa Fork y crea
CalTools en tu cuenta. Si ya existe https://github.com/peauelea96/CalTools,
utiliza ese fork. No necesitas crear otro.

B. Clonar el fork en el disco ORICO
Conecta el disco. Si no aparece /Volumes/ORICO, no continúes con esta ruta.
Prepara la carpeta contenedora y entra en ella:
  mkdir -p "/Volumes/ORICO/MASTER EMOS/Segundo/Segundo Cuatri/BECA INE/Calibrado"
  cd "/Volumes/ORICO/MASTER EMOS/Segundo/Segundo Cuatri/BECA INE/Calibrado"

Si ya existe una carpeta CalTools, no la sobrescribas ni la borres: comprueba
si es tu clon actual y utiliza la sección 4 o 5.
Si no existe:
  git clone "https://github.com/peauelea96/CalTools.git" "CalTools"
  cd "/Volumes/ORICO/MASTER EMOS/Segundo/Segundo Cuatri/BECA INE/Calibrado/CalTools"

C. Añadir el original como upstream y ajustar los permisos
  git remote add upstream "https://github.com/pgsegador/CalTools.git"
  git config core.filemode false

core.filemode false es una configuración local de este clon. Hace que Git
ignore diferencias del permiso de ejecución que pueden aparecer en ORICO.
No ignora cambios de contenido ni arregla permisos de lectura o escritura.
No hace falta repetirla en cada sesión; sí en un clon nuevo.

D. Crear desarrollo y subirla al fork
Primero comprueba las ramas:
  git branch -a

Si desarrollo no existe ni localmente ni como origin/desarrollo:
  git switch -c desarrollo
  git push -u origin desarrollo

Esto crea desarrollo desde la rama actualmente clonada y enlaza su seguimiento
con origin/desarrollo. Si ya existe localmente, usa git switch desarrollo.
Si solo existe en el fork, usa:
  git switch --track origin/desarrollo

E. Comprobar
  pwd
  git status
  git branch -vv
  git remote -v
  git config --get core.filemode

Debes estar en la ruta indicada, en desarrollo, con seguimiento de
origin/desarrollo; origin debe ser el fork y upstream el original.
core.filemode debe devolver false. Si no has editado archivos, el estado
debería indicar «nothing to commit, working tree clean».

4. ALTERNATIVA: YA CLONASTE EL ORIGINAL DEL TUTOR
==============================================
No es necesario volver a descargarlo. Primero crea o confirma tu fork en
GitHub y comprueba lo que tienes:
  cd "/Volumes/ORICO/MASTER EMOS/Segundo/Segundo Cuatri/BECA INE/Calibrado/CalTools"
  git status
  git remote -v
  git branch -vv

Si origin apunta al original y NO existe upstream:
  git remote rename origin upstream
  git remote add origin "https://github.com/peauelea96/CalTools.git"

Si upstream ya apunta al original y origin también apunta al original,
cambia únicamente origin:
  git remote set-url origin "https://github.com/peauelea96/CalTools.git"

Si ya están bien, no cambies los remotos. Si hay otra configuración, no
ejecutes estas alternativas a ciegas: identifica las URL primero.
Comprueba también cualquier URL específica de envío:
  git remote get-url --push --all origin

Todas las URL de envío de origin deben corresponder a tu fork. Si aparece
el original o una URL inesperada, detente antes de hacer push.

Después:
  git config core.filemode false
  git fetch origin
  git branch -a

Con el árbol limpio, crea desarrollo si no existe (git switch -c desarrollo),
o cambia a ella si ya existe (git switch desarrollo). Si solo existe en el
remoto, usa git switch --track origin/desarrollo.
Si hay cambios sin guardar en Git, revísalos y guárdalos antes de cambiar
de rama; no los descartes para conseguir un estado limpio.

Comprueba que desarrollo contiene el trabajo que quieres subir:
  git log --oneline -5
  git push -u origin desarrollo
  git branch -vv
  git remote -v

El -u establece seguimiento del fork aunque la rama antes siguiera upstream.
Si el push es rechazado, consulta la sección 9. No fuerces el envío.

5. RUTINA DIARIA: EMPEZAR Y TRABAJAR
==================================
Cada vez que abras una terminal nueva:
  cd "/Volumes/ORICO/MASTER EMOS/Segundo/Segundo Cuatri/BECA INE/Calibrado/CalTools"
  pwd
  git status
  git branch --show-current
  git remote -v

Si estás en desarrollo, continúa. Si estás en otra rama, revisa y guarda
cualquier cambio pendiente antes de ejecutar:
  git switch desarrollo

Para consultar cambios que puedan haberse subido al fork desde otro equipo:
  git fetch origin
  git status

Si el árbol está limpio y no hay una operación Git pendiente, actualiza desde
la misma rama de tu fork:
  git pull --ff-only origin desarrollo

Si se detiene por divergencia, no fuerces: revisa la sección 9. Esta actualización
del fork es distinta de incorporar novedades del tutor (sección 7).

Abre el proyecto en RStudio:
  open "CalTools.Rproj"
Si no se abre con RStudio:
  open -a "RStudio" "CalTools.Rproj"

Edita los archivos y guárdalos en RStudio. Puedes consultar en cualquier momento:
  git status
  git diff

git diff muestra cambios de archivos ya seguidos; los archivos nuevos aparecen
en git status y debes revisarlos en el editor. Ejecuta las comprobaciones de R
adecuadas al cambio antes de registrarlo. Una sesión nueva no requiere repetir
fork, clone ni gh auth login si tu sesión sigue siendo válida.

6. GUARDAR AVANCES: ADD, COMMIT Y PUSH
====================================
Antes de publicar, confirma la rama y el destino:
  git branch --show-current
  git remote get-url --push --all origin
  git status
  git diff

Debe ser desarrollo y la URL de tu fork. Selecciona solo los archivos deseados.
Ejemplo: sustituye esta ruta por un archivo que realmente hayas modificado:
  git add "R/nombre_del_archivo.R"

No uses git add . por costumbre: puede incluir datos, resultados, credenciales
o archivos personales. Revisa la selección completa:
  git diff --cached
  git diff --cached --name-only

Si seleccionaste por error un archivo, puedes quitarlo del próximo commit sin
borrar su contenido (en este repositorio, que ya tiene historial):
  git restore --staged "ruta/al/archivo"

Cuando todo esté correcto:
  git commit -m "Explica brevemente el cambio realizado"
  git push origin desarrollo
  git status

El commit guarda en tu ordenador; el push publica en tu fork. Si otros archivos
quedan pendientes, git status seguirá mostrándolos: no implica que el push falló.
En GitHub, abre tu fork y selecciona desarrollo para comprobar los archivos.

7. INCORPORAR ACTUALIZACIONES DEL TUTOR CON PRECAUCIÓN
===================================================
No necesitas hacerlo en cada sesión. Hazlo cuando quieras incorporar novedades
del original y tengas tiempo para revisar y comprobar el resultado.

A. Preparar
En desarrollo, termina y registra los cambios propios. Requiere árbol limpio,
sin conflictos ni operaciones pendientes. Comprueba también la actualización
de tu fork mediante la sección 5. Después:
  git status
  git branch --show-current
  git fetch upstream
  git remote show upstream

Busca «HEAD branch» en la última salida: indica la rama predeterminada del
original. No suponemos que se llame main o master.

B. Crear una referencia de respaldo local
  git branch "respaldo-desarrollo-antes-upstream-20261014"

Usa la fecha del día y un nombre nuevo en cada ocasión. Si ya existe, elige
otro; no lo sobrescribas. El respaldo protege commits, no archivos sin registrar.

C. Revisar antes de integrar
En los siguientes comandos SUSTITUYE RAMA_ORIGINAL por el nombre encontrado:
  git log --oneline desarrollo..upstream/RAMA_ORIGINAL
  git diff --stat desarrollo...upstream/RAMA_ORIGINAL

El primero lista commits del original que desarrollo no contiene; el segundo
resume cambios del original desde el ancestro común. Si entiendes y quieres
incorporar esos cambios:
  git merge --no-edit upstream/RAMA_ORIGINAL

Esto integra el original en tu desarrollo local, conservando tus commits.
Puede generar un commit de combinación o avanzar directamente si es posible.

D. Si hay conflictos
No hagas push. git status identifica los archivos afectados. Si no sabes
resolverlos, puedes cancelar la combinación que sigue en curso:
  git merge --abort

Con el árbol limpio antes de comenzar, esto permite volver al estado anterior
de la combinación. No sirve para deshacer un merge ya terminado.
Si decides resolverlos, edita los archivos, elimina las marcas de conflicto,
verifica el resultado, añade solo los archivos resueltos y completa el commit:
  git add "ruta/al/archivo_resuelto"
  git commit

E. Verificar y publicar
Comprueba que CalTools sigue funcionando y revisa:
  git status
  git log --oneline -5
  git push origin desarrollo

Todo se publica en tu fork. No hace falta enviar nada a upstream ni abrir
una pull request para mantener tu copia actualizada.

9. PROBLEMAS FRECUENTES Y SEGURIDAD
=================================
«No such file or directory» al hacer cd:
  Comprueba que ORICO está conectado y que la ruta es exacta. No sigas si cd
  falla: podrías estar trabajando en otra carpeta.

«not a git repository»:
  Comprueba pwd y entra en CalTools. No ejecutes git init para intentar arreglar
  un clon existente sin comprender qué ha ocurrido.

«remote ... already exists» o «branch ... already exists»:
  Consulta git remote -v o git branch -a y usa lo que ya existe. No repitas
  la configuración inicial ni borres elementos para ocultar el error.

Push rechazado por autenticación:
  Usa gh auth status, confirma la cuenta y, si es necesario, gh auth login
  y gh auth setup-git. Comprueba que origin apunta a tu fork.

Push rechazado porque hay cambios remotos / pull --ff-only no puede avanzar:
  Con trabajo guardado y árbol limpio, usa git fetch origin y revisa:
    git log --oneline --graph --decorate -15 desarrollo origin/desarrollo
  Puede que ambas copias hayan avanzado. Detente y revisa cómo integrarlas;
  no uses --force. La combinación requiere valorar los cambios y conflictos.

«nothing to commit»:
  No hay cambios preparados para registrar; comprueba git status y que guardaste
  el archivo en el editor y en la carpeta correcta.

Reglas para proteger tu trabajo y el repositorio del tutor:
  - Usa git push origin desarrollo, con origin verificado como tu fork.
  - No ejecutes git push upstream, ni --all, --mirror o --force.
  - No hagas reset --hard: puede perder cambios locales. No uses limpieza
    destructiva para resolver un estado que no entiendes.
  - No publiques contraseñas, tokens, datos personales ni datos restringidos.
    El fork puede ser público; el tutor y otras personas podrían leerlo.
    Publicar en el fork no modifica su original, pero no ofrece privacidad.
  - Una PR al original sí es una propuesta dirigida al tutor y puede generar
    notificaciones. Revisa el destino antes de crearla.
  - Opcionalmente, puedes bloquear los push accidentales a upstream:
      git remote set-url --push upstream "https://example.invalid/NO_PUBLICAR"
    Solo cambia la URL de envío en este clon; fetch seguirá usando el original.
    Desde entonces git remote -v mostrará una URL distinta para upstream (push).
    Puedes restaurarla conscientemente con:
      git remote set-url --push upstream "https://github.com/pgsegador/CalTools.git"

10. ORICO, GOOGLE DRIVE Y LA CARPETA .git
=======================================
Google Drive sincroniza archivos; Git gestiona historial y operaciones que
pueden modificar varios archivos internos a la vez. La carpeta oculta .git
contiene historial, ramas, configuración e índices: no la edites ni la borres,
y no combines manualmente copias de sus archivos creadas por Drive.

La opción más fiable es tener el clon de trabajo fuera de la sincronización
activa de Drive y usar GitHub para compartir commits entre equipos. Puedes
guardar copias de seguridad adicionales, pero Drive no sustituye a Git.
Si conservas esta ubicación sincronizada, evita trabajar en dos equipos sobre
la misma carpeta y pausa la sincronización durante operaciones Git. Eso reduce
interferencias, pero no garantiza la integridad del repositorio.

Antes de desconectar ORICO, termina operaciones, cierra el proyecto y expulsa
el disco correctamente. Si Drive genera copias en conflicto o Git avisa de
corrupción, detente, conserva una copia del trabajo y pide ayuda antes de borrar
archivos o intentar reconstruir .git. Un push no respalda archivos ignorados
ni cambios sin commit; esos necesitan su propia copia de seguridad.
